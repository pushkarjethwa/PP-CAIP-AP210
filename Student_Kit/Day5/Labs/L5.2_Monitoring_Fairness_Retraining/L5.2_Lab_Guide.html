Objective & scenario alignment

Horizon Gulf Bank (HGB) is a fictional UAE retail bank with 250,000 customers. Its Board approved Project MIZAN — an AI decisioning platform covering credit, fraud, collateral valuation, cash logistics, customer retention and document automation. You are a junior ML practitioner in the MIZAN squad.

It is 1 December 2025. MIZAN fraud v1.0.0 has been live for two months; chargeback labels for October and November have now arrived. The Model Risk Committee meets tomorrow and wants a monitoring report: is the model still fit for purpose, is it fair, is it robust, and if not, what replaces it?

Progressive architecture: monitors the exact package and registry you built in L5.1, and the credit policy from L3.1.

By the end of this lab you will be able to

  • Compute production features with the shared module and a history warm-up
  • Build a data-quality/schema monitor with OK/WARN/FAIL status
  • Measure data drift per feature with PSI, and prediction drift via alert rates
  • Measure weekly performance decay and diagnose concept drift by segment
  • Run fairness (disparate impact, equal opportunity) and robustness/evasion checks
  • Retrain a challenger, compare champion vs challenger on a later period, and record the decision in the registry

1Load the champion and build production features with warm-up 10 min

Why this matters

Production features must come from the same module as training and need each card’s history (velocity windows, ‘first time in country’). We prepend Apr–Sep history, build features, and keep the production rows. Labels (is_fraud) are now available for Oct–Nov.

Your tasks

  1. Import mizan_fraud.features and load the champion model + model card from the package.
  2. Load history and production raw files; build features on their concatenation; keep production rows as pf; add week.
  3. Load the training reference features (split == 'train') as ref.
Checkpoint — you should see

402k production rows over ≈ 9 weeks.

2Data-quality and schema monitor 12 min

Why this matters

Schema problems are the most common production incident and the easiest to catch. We derive expectations from training — allowed categories, null rates, value ranges — and test production against them with a traffic-light status.

Your tasks

  1. Write expectations(ref) → per feature: allowed categories (categoricals), null rate, 0.1%/99.9% quantiles (numerics).
  2. Write dq_check(pf, exp) → table with check, observed, status (OK / WARN / FAIL): unseen categories = FAIL; null rate +2 pts = WARN, +5 pts = FAIL; >1% of values outside the reference range = WARN.
  3. Show only non-OK rows.
Checkpoint — you should see

Three FAILs: unseen Digital_Wallet channel, unseen UNKNOWN merchant category, and merchant_risk_score null rate +7 pts (upstream enrichment outage).

Think like a practitioner

The model handles unseen categories (encoded −1) without crashing. Why is a FAIL still the right status?

3Data drift (PSI) and prediction drift 12 min

Why this matters

PSI quantifies how far each feature’s distribution has moved. Prediction drift — the alert rate — is visible immediately, weeks before labels. Together they are the leading indicators.

Your tasks

  1. Implement psi(expected, actual, bins=10) with quantile bins from the reference and ε-clipping.
  2. PSI for every numeric feature: reference vs October and vs November. Flag 0.1 (warn) and 0.25 (act).
  3. Score production with the champion; plot the weekly alert rate against the 0.5% design rate.
Checkpoint — you should see

Almost every feature is stable (PSI < 0.05). The exception is card_txn_index (WARN, ≈ 0.2): it counts each card’s history, so it grows with time by construction — a non-stationary feature that should be replaced (e.g. by transactions per month of tenure). The weekly alert rate stays near the fraud rate, so prediction drift alone would not raise an alarm.

💡 Hint

np.unique on the quantile edges avoids empty bins for features with many identical values (flags, counts).

4Performance decay and concept-drift diagnosis 14 min

Why this matters

Now the lagging truth. With labels we measure recall at the operational threshold week by week and compare it with the September test value on the model card. Then we slice by channel and 3DS status to find where the model fails — the signature of concept drift.

Your tasks

  1. Weekly table: frauds, recall at THR (alerted frauds / frauds), precision at THR, PR-AUC. Add the model-card reference recall line.
  2. Slice November recall by channel and by is_3ds_authenticated for e-commerce.
  3. Write a 3-line diagnosis in markdown.
Checkpoint — you should see

Weekly recall at the threshold ≈ 0.58–0.74 vs ≈ 0.88 on the September test — a drop well beyond the 10-point trigger. November recall on Digital_Wallet fraud ≈ 4% and on 3DS-authenticated e-commerce fraud ≈ 50% (vs ≈ 85% non-3DS): the new scam typology. Classic concept drift.

Think like a practitioner

Would re-tuning the threshold fix this? Why or why not? (No — the scam scores low; lowering the threshold floods Ops with false alerts.)

5Responsible AI: fairness of the credit policy and robustness of the fraud model 14 min

Why this matters

Governance is part of maintenance. For credit (L3.1) we test whether approval outcomes differ by gender or nationality group — attributes the model never saw but could reach through proxies. The disparate-impact ratio (lowest ÷ highest approval rate; < 0.8 is a red flag) and equal opportunity (approval rate among borrowers who actually repaid) are standard metrics. For fraud we run an evasion probe: do fraudsters slip through if they split amounts or reuse a known device?

Your tasks

  1. Load credit_model.joblib, credit_policy.json and the L1.2 test split. Approve if PD < cut-off.
  2. Table by gender and by nationality_group: approval rate, approval rate among repayers (equal opportunity), default rate among approved. Compute the disparate-impact ratio for each attribute.
  3. Evasion probe: take alerted fraud in November, (a) halve amount_aed-derived features, (b) set is_new_device = 0; re-score and report the share still alerted.
Checkpoint — you should see

Gender DI = 1.00; nationality DI ≈ 0.94 (Emirati ≈ 95.6% vs African ≈ 90.2% approval) — inside the 4/5 rule, and default rates among approved applicants differ in the same direction (≈ 3.2% vs 4.9%), consistent with genuine risk differences via salary/employer. Evasion: ≈ 94% of caught fraud stays alerted when amounts are halved, ≈ 89% when a known device is faked — velocity features make the model fairly robust.

Think like a practitioner

The nationality DI ratio is below 0.8 but default rates among approved applicants are similar across groups. Is the model unfair, or is it reflecting real risk differences? What would you recommend?

6Retrain a challenger, compare, decide, and write the report 18 min

Why this matters

Retraining on recent labelled data teaches the model the new scam pattern. A fair champion–challenger test trains the challenger on data up to October and compares both models on November only — data neither has seen. The decision and its evidence go to the registry and into the committee report.

Your tasks

  1. Challenger training set: training-reference fraud + legit sample plus all October production rows (undersampled the same way). Same algorithm and hyperparameters as the champion.
  2. Evaluate champion vs challenger on November: recall@0.5% budget, PR-AUC, recall on Digital_Wallet and 3DS-authenticated e-commerce fraud.
  3. Promote if the challenger improves November PR-AUC by ≥ 0.02 with no slice worse by > 5 pts: register it as a new MLflow version and move the champion alias; else tag it challenger.
  4. Assemble monitoring_report_2025Q4.html with the DQ issues, drift, weekly performance, fairness tables, probes and decision.
Checkpoint — you should see

Challenger PR-AUC ≈ 0.76 vs 0.69 (+0.065) with no slice worse → PROMOTE; registry v2 takes the champion alias; the HTML report is written. But Digital_Wallet recall only rises from ≈ 4% to ≈ 15%: retraining helps, yet the scam typology needs new features (payee age, first-time beneficiary, call-centre signals) — say so in the report.

Think like a practitioner

The challenger learned October’s scam pattern from October labels. What is the risk of data poisoning in this loop, and which control would you add? (label provenance, chargeback-only labels, anomaly checks on new training data, human sign-off)
