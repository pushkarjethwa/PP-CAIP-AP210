Objective & scenario alignment

Horizon Gulf Bank (HGB) is a fictional UAE retail bank with 250,000 customers. Its Board approved Project MIZAN — an AI decisioning platform covering credit, fraud, collateral valuation, cash logistics, customer retention and document automation. You are a junior ML practitioner in the MIZAN squad.

The card-authorisation platform team will integrate MIZAN fraud scoring next sprint. They need: a versioned package, an API contract, a threshold that produces ≈ 0.5% alerts, latency evidence, a model card for Model Risk, and an automated gate in the release pipeline.

Progressive architecture: the package you build is what Lab L5.2 monitors in production.

By the end of this lab you will be able to

  • Remove training–serving skew by moving feature code into a module, and prove parity
  • Understand why real-time features need history (feature store)
  • Track candidate models in MLflow; select, refit and register a champion with an alias
  • Write a model card (intended use, data, metrics, limitations, owners)
  • Serve the model with FastAPI + Pydantic validation; test with TestClient; measure latency
  • Run a batch-scoring job on new raw data and a CI quality gate

1Move feature code into a module and prove parity 12 min

Why this matters

If training computes features in a notebook and serving re-implements them in Java, they will diverge — training–serving skew, a top cause of silent production failures. One module, imported by both, removes the risk. A parity test proves the module reproduces the training features exactly.

Your tasks

  1. Create the package folder checkpoints/mizan_fraud/ (+ __init__.py, model/) and write features.py containing build_fraud_features, NUMF, CATF with a %%writefile cell.
  2. Import it; rebuild features from the raw file; compare with card_features.parquet on 50k random txn_ids (np.allclose, NaN-aware).
  3. Now rebuild using only September raw data and measure how many card_txn_index / secs_since_prev values differ. Explain why.
Checkpoint — you should see

Parity True. With September-only data, most card_txn_index values and many secs_since_prev values differ — velocity features need each card’s history, which in production comes from a feature store.

Think like a practitioner

The authorisation system sends one transaction at a time. Where do txn_count_1h and amount_vs_card_mean come from at that moment?

2Track candidate models in MLflow 15 min

Why this matters

Three people tuning the same model in three notebooks is chaos. Experiment tracking records every candidate’s parameters, metrics and artefacts in one queryable store. We train three random-forest candidates on train, evaluate on validation at the 0.5% budget, and log everything.

Your tasks

  1. Point MLflow at sqlite:///checkpoints/mlflow/mlflow.db; create/get experiment mizan-fraud with artefacts under checkpoints/mlflow/artifacts.
  2. Undersample train (all fraud + 250k legit). For 3 configs of (n_estimators, min_samples_leaf, max_features) fit an RF pipeline, compute at_budget on valid, and log params + metrics + training time in a run.
  3. Query the runs into a DataFrame with mlflow.search_runs and pick the best by PR_AUC.
Checkpoint — you should see

Three runs logged; PR-AUC differences are small (≈ 0.94 ± 0.01) but training times differ a lot — a real trade-off to document.

💡 Hint

Run mlflow ui --backend-store-uri sqlite:///checkpoints/mlflow/mlflow.db in a terminal to browse runs in the browser.

3Refit, set the alert threshold, write the model card, register the champion 15 min

Why this matters

The chosen configuration is refit on train + valid (more, and more recent, data). The alert threshold is set so that ≈ 0.5% of validation traffic alerts — the operational budget. A model card documents intended use, data, performance, limitations and owners; Model Risk will not approve a model without one. The registry alias champion is what deployment uses.

Your tasks

  1. Compute threshold = the 99.5th percentile of the candidate’s validation scores.
  2. Refit best_cfg on undersampled train+valid; evaluate at_budget on test.
  3. Save fraud_rf.joblib and model_card.json into mizan_fraud/model/.
  4. Log a final run with the artefacts, register it as mizan-fraud, and set alias champion.
Checkpoint — you should see

Threshold ≈ 0.3–0.6 (undersampled scores); test alert rate ≈ 0.4–0.6%; test recall@0.5% ≈ 0.9.

Think like a practitioner

The card says ‘NOT for automatic card blocking’. Why does the intended-use statement matter legally and operationally?

4Serve it: FastAPI with Pydantic validation 15 min

Why this matters

The authorisation platform calls a contract, not a notebook. Pydantic enforces types and ranges and an allow-list of channels; malformed or hostile input never reaches the model. /health exposes the live version for observability.

Your tasks

  1. Write mizan_fraud/app.py with %%writefile: Pydantic Txn schema, endpoints /health, /score, /score_batch.
  2. With TestClient: call /health; score 3 real test transactions (one known fraud); send 2 invalid payloads (negative amount, unknown channel) and confirm HTTP 422.
  3. Note the command to run it live: uvicorn mizan_fraud.app:app --port 8000 from the checkpoints folder.
Checkpoint — you should see

/health shows v1.0.0; the fraud row gets a high score and alert: true; invalid payloads return 422 naming the bad field.

💡 Hint

Pydantic rejects NaN in JSON, so convert NaN to None (JSON null) — the model’s imputer handles it.

5Load test: latency and throughput 10 min

Why this matters

An authorisation SLA is typically p95 < 50–100 ms end-to-end. We measure the service’s latency distribution on 300 single calls and the throughput of /score_batch on 5,000 transactions. Averages hide tail latency — always report percentiles.

Your tasks

  1. Send 300 single /score requests; record wall-clock latency; report p50/p95/p99.
  2. Send one /score_batch request with 5,000 transactions; report transactions/second.
Checkpoint — you should see

Single-call p95 in the tens of ms on a laptop (RF with n_jobs=-1 per call adds overhead); batch throughput thousands of txns/s.

Think like a practitioner

p95 is 60 ms and the SLA is 50 ms. List three fixes in order of effort.

6Nightly batch job on new raw data + CI release gate 13 min

Why this matters

Not everything is real-time: Fraud Ops also wants a nightly batch report on the previous day. The batch job must use the same feature module with history warm-up. Finally a release gate encodes our standards as code; its JSON output is the evidence attached to the change ticket.

Your tasks

  1. Batch job: concatenate raw history (Aug–Sep) with the first production week (1–7 Oct), build features with the module, keep October rows, score them, count alerts per day.
  2. Write release_gate(model, card) checking: test PR-AUC ≥ 0.85, test alert rate between 0.3% and 0.8%, p95 latency < 150 ms, no ID/PII features, threshold in (0,1). Save release_gate.json and print DEPLOY/BLOCK.
Checkpoint — you should see

Daily alert rates wander between ≈ 0.3% and 0.6%. Compare alerts with fraud: on several days the model alerts far fewer transactions than there are frauds — an early hint of trouble (new Digital_Wallet channel, new scam typology). All gate checks pass → DEPLOY.

Think like a practitioner

The gate passed, yet the batch job already shows an unusual alert rate. Is that a deployment problem or a monitoring problem? (→ Lab 5.2)

Stretch challenges

  1. Containerise: write a Dockerfile (python:3.12-slim, copy mizan_fraud/, pip install, CMD uvicorn …). What goes in .dockerignore?
  2. Replace TestClient with a live uvicorn server and load-test with httpx.AsyncClient (50 concurrent requests).
  3. Add an /explain endpoint that returns the top 3 contributing features for a transaction (e.g. by perturbation).

Troubleshooting

  • UnsupportedModelRegistryStoreURIException → you installed mlflow-skinny; run pip install mlflow (needs SQLAlchemy).
  • 422 on every request → a NaN slipped into the JSON; use the payload() helper.
  • ModuleNotFoundError: mizan_fraud → sys.path.insert(0, str(CKPT)) must run first.
