Objective & scenario alignment

Horizon Gulf Bank (HGB) is a fictional UAE retail bank with 250,000 customers. Its Board approved Project MIZAN — an AI decisioning platform covering credit, fraud, collateral valuation, cash logistics, customer retention and document automation. You are a junior ML practitioner in the MIZAN squad.

Capstone brief. The Retention Committee approved the churn programme on one condition: the model must go live the way a regulated bank deploys models. Working in teams of 3–4, you will package the champion, prove it is fair and explainable, register it, serve it securely, generate the first campaign list, rehearse what happens when the population drifts and when a bad model version is pushed — and present the result to the committee (5 minutes per team).

Progressive architecture: this lab consumes artefacts from all four previous days and uses the same MLflow database as L5.1.

By the end of this lab you will be able to

  • Verify model integrity with a SHA-256 hash recorded in the model card
  • Run a responsible-AI gate: disparate impact and equal opportunity by gender, nationality group and age band
  • Generate model-agnostic reason codes for every decision
  • Register and alias the model in MLflow behind an automated release gate
  • Serve it with FastAPI: schema validation, API-key access control, audit log, human-in-the-loop flag
  • Produce the campaign list, simulate a drifted quarter (PSI) and rehearse a rollback

1Package the champion and prove its integrity 8 min

Why this matters

Before anything is deployed, Model Risk must be sure the artefact is exactly the one that was validated. A SHA-256 hash of the file is its fingerprint: any change — retraining, tampering, corruption — changes the hash. We re-score the test set to prove the packaged model reproduces the validated metric.

Your tasks

  1. Create CKPT/mizan_churn/model/; copy the L3.4 bundle there, adding reference values (training medians/modes) and risk bands (score at the 80th and 90th percentile of training).
  2. Compute the SHA-256 of the saved file.
  3. Re-score the L3.4 test split and assert the PR-AUC matches the bundle's recorded value.
Checkpoint — you should see

Logistic champion packaged; the hash is printed; test PR-AUC 0.2514 reproduced exactly; MEDIUM starts at P(churn) ≈ 0.18, HIGH at ≈ 0.24.

Think like a practitioner

Why does a hash of the file prove integrity better than re-checking the accuracy?

2Responsible-AI gate: fairness and reason codes 15 min

Why this matters

Gender and nationality are not model inputs — but features can act as proxies. The gate measures outcomes: the disparate impact ratio (each group's rate of being selected for the HIGH band ÷ the highest group's rate; the 4/5 rule flags < 0.8) and equal opportunity (true-positive rate among actual churners per group). Being selected for a retention offer is a benefit, so under-selection is the harm to look for. Then every decision gets reason codes.

Your tasks

  1. On the test split add high = p ≥ band_high, and an age_band (18–29, 30–44, 45–59, 60+).
  2. For gender, nationality group and age band compute: size, selection rate, DI ratio, TPR and the equal-opportunity ratio (TPR ÷ best TPR). Flag DI < 0.8 as REVIEW and EO < 0.7 as BLOCK.
  3. Write reason_codes(row): set each feature in turn to its reference value and record how much P(churn) falls; return the top 3. Show them for the 3 riskiest test customers.
Checkpoint — you should see

Gender is balanced (DI ≈ 0.99). Emirati (DI ≈ 0.61) and Western (≈ 0.67) customers are flagged REVIEW — they are selected less often, and the 60+ band (small, 651 customers) is selected most. Equal-opportunity ratios stay ≥ 0.7 for gender and nationality (lowest ≈ 0.74, Emirati), so nothing is BLOCKed — but it is close. Reason codes for the riskiest customers cite complaints, no salary transfer and inactivity, with the percentage points each adds.

Think like a practitioner

Emirati customers churn less (e.g. more salary transfers), so lower selection may be accurate. Is a DI flag automatically discrimination? Why is equal opportunity (TPR) the fairer test for a benefit allocated by risk — and why is 0.74 still worth escalating?

3Register behind an automated release gate 12 min

Why this matters

The registry is the single source of truth for which model is live. A release gate — code, not a meeting — checks minimum performance, fairness, forbidden features and integrity before the champion alias can move. Every check and its evidence is stored, so auditors can replay the decision.

Your tasks

  1. Write model_card.json (name, version 1.0.0, intended use, data, metrics, fairness summary, limitations, owners, hash).
  2. Write release_gate(metrics, min_di, feats, digest) → dict of named checks; passed = all true.
  3. Log an MLflow run in experiment mizan-churn (params, metrics, artefacts); register mizan-churn; set alias champion only if the gate passes.
Checkpoint — you should see

All five checks pass (DI flags are documented in the card's limitations but are not blocking); version registered and aliased champion.

Think like a practitioner

The committee wants DI ≥ 0.8 for nationality to block release. Change one line of the gate. What else would have to change before the model can ship?

4Serve it securely: validation, API key, reason codes, audit log 15 min

Why this matters

The CRM calls the service, not the notebook. Pydantic rejects malformed or out-of-range input; an API key header is the minimum access control (production adds mTLS/OAuth and a secrets manager); every decision is written to an audit log with a request id and model version; high-value, high-risk customers are routed to a human relationship manager.

Your tasks

  1. Write mizan_churn/app.py with %%writefile (schema, /health, /score with key check, reason codes, audit log, human_review flag).
  2. With TestClient: /health; score the riskiest test customer with the key; call without the key (expect 401); send an invalid payload (expect 422).
  3. Show the last audit-log line.
Checkpoint — you should see

/health shows version 1.0.0 and the hash prefix. The riskiest customer scores 0.76 (HIGH) with 3 reason codes (complaints +21 pts, no salary transfer +19 pts, 31 idle days +13 pts) in ≈ 10 ms; no key → 401; invalid emirate and age → 422 naming both fields; the audit line has request id, score and model version.

💡 Hint

customer_id, avg_balance_aed and monthly_salary_aed are raw inputs — the service derives log_balance/log_salary itself, exactly like training.

5Batch job: the first retention campaign 10 min

Why this matters

Real-time scoring serves the call-centre screen; the campaign itself is a batch job over the whole base. We score all customers, rank by expected value (L3.4), keep the 10% budget, attach reason codes and write the file the CRM imports.

Your tasks

  1. Score all 250k customers with the packaged model; compute EV as in L3.4.
  2. Take the top 10% by EV; add the top-2 reason codes for each (use the first 2,000 rows to keep it quick, mark the rest ‘batch-later’).
  3. Write retention_campaign.csv; print the band mix and expected value of the campaign.
Checkpoint — you should see

25,000 customers with ≈ AED 1.62M expected value. The list is not only HIGH-band (≈ 8.1k HIGH, 4.9k MEDIUM, 12.0k LOW): EV ranking pulls in wealthy lower-risk customers. Reasons read like ‘complaints_12m=3; salary_transfer=0’.

Think like a practitioner

A relationship manager asks why their client is on the list with P(churn) = 0.09. What do you show them?

6Next quarter: simulate drift and decide 15 min

Why this matters

Q1 2026 brings a mobile-app outage (logins fall), a complaints spike and a competitor's salary-transfer campaign. PSI per feature quantifies the data drift; PSI on the scores quantifies prediction drift. Without labels yet (churn is only known 6 months later) these are the early-warning signals that trigger investigation or retraining.

Your tasks

  1. Create q1 from a 50k sample: logins × 0.6; +1 complaint for 15% of customers; 10% of salary-transfer customers lose it.
  2. Write psi(ref, new, bins=10) with quantile bins from the reference; compute PSI for every numeric feature and for the scores.
  3. Apply the policy: PSI < 0.1 stable · 0.1–0.25 investigate · > 0.25 retrain trigger. Print the decision.
Checkpoint — you should see

digital_logins_30d has an enormous PSI (≈ 4.7 — the whole distribution moved), complaints ≈ 0.09, salary transfer ≈ 0.02; the score PSI is ≈ 0.22, mean P(churn) rises 0.12 → 0.17 and the HIGH band more than doubles (10% → ≈ 22%). Decision: RETRAIN TRIGGER — but first check whether the login drop is a data/outage artefact rather than real behaviour.

Think like a practitioner

The call-centre budget is fixed at 10%. If the HIGH band doubles, do you recalibrate the band thresholds or call more customers? Who decides?

7Rollback drill and the committee summary 15 min

Why this matters

Someone will eventually push a broken model. Here a broken join silently zero-fills three features (salary transfer, complaints, days since last transaction). The gate must catch it, the champion alias must stay on v1, and the team must know the one-line rollback. Then you assemble the numbers for the 5-minute committee presentation.

Your tasks

  1. Build v2: refit the champion's pipeline on training data where salary_transfer, complaints_12m and days_since_last_txn are 0; score test the same way (bug included).
  2. Run release_gate on v2 (save its artefact and hash it); register it as a new version; do not move the alias if it fails.
  3. Resolve mizan-churn@champion → version; write churn_release_gate.json and capstone_summary.md (headline metrics, fairness, campaign, drift decision, L4.3 challenger decision).
Checkpoint — you should see

The candidate's PR-AUC drops to ≈ 0.21 and capture@10% below 0.22 → both performance checks fail → REJECTED; the champion alias stays on the v1.0.0 version. (Registry version numbers grow each time you re-run — that is the point of a registry.) The summary prints the headline numbers for the presentation.

Think like a practitioner

The bug was caught by a performance check. Which cheaper check — run before any training — would have caught it earlier? (Hint: a data-contract test on feature variance.)

Troubleshooting

  • ModuleNotFoundError: mizan_churn → the %%writefile path is relative to this notebook's folder; run from Day5/Labs/L5.3_….
  • MLflow ‘database is locked’ → close any running mlflow ui that points at the same file.
  • 422 on a valid customer → a NaN slipped into the payload; convert NaN to None.
