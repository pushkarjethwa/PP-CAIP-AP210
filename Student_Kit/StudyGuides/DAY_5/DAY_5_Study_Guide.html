1. Training vs Inference and Model Serialisation

What & Why

Training is the expensive, offline step that learns parameters from historical data. Inference (scoring) applies the frozen model to new data, and must be fast, reliable and reproducible. To move a model from a notebook to production you serialise it into a model artefact (a file) that another process loads.

  • scikit-learn: joblib.dump / joblib.load (pickle-based). Save the whole Pipeline so preprocessing travels with the model.
  • Keras: model.save("model.keras") and keras.models.load_model.
  • Portable formats such as ONNX exist for cross-framework serving.
  • Record the library versions used; artefacts can break across versions.

Security: pickle/joblib files can execute code when loaded. Only load artefacts from a trusted, access-controlled registry; never from an untrusted source.

AnalogyTraining is writing and printing a cookbook; inference is a cook following one recipe, quickly, a thousand times a day. The artefact is the printed recipe card that must reach the kitchen intact.
Finance example

The fraud-scoring pipeline is trained overnight, saved with its scaler and feature list, and loaded by a scoring service that must answer in milliseconds for each card swipe.

Save and reload a whole pipeline, with metadata
import json, joblib, sklearn
from datetime import datetime, timezone

# `model` is a fitted sklearn Pipeline (preprocessing + estimator)

2. Batch vs Real-time Inference and Serving a Model as a Service

What & Why
  • Batch inference: score many records on a schedule (nightly churn list, monthly credit-line review). Simple and cheap; results can be stale.
  • Real-time (online) inference: score one request on demand behind an API (card authorisation, instant loan pre-approval). Needs low latency, high availability and scaling.
  • Typical service design: load the model once at startup, validate the input schema, return the score plus the model version, log every request, and add health checks and authentication.
AnalogyBatch is a bakery baking tomorrow's bread overnight; real-time is a barista making each coffee when the customer orders.
Finance example

Card fraud scoring must answer inside the payment authorisation window, so it is a real-time service. The monthly "who may deserve a limit increase" list is a batch job.

A minimal FastAPI scoring service (save as app.py, run: uvicorn app:app)
import joblib
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI(title="Fraud Scoring Service")
MODEL = joblib.load("fraud_model_v1.joblib")          # load once, at startup
MODEL_VERSION = "1.0.0"

class Txn(BaseModel):                                  # input validation (schema)
    amount_aed: float = Field(ge=0)
    merchant_risk_score: float = Field(ge=0, le=1)
    distance_from_home_km: float = Field(ge=0)

@app.get("/health")
def health():
    return {"status": "ok", "model_version": MODEL_VERSION}

@app.post("/score")
def score(t: Txn):
    row = [[t.amount_aed, t.merchant_risk_score, t.distance_from_home_km]]
    p = float(MODEL.predict_proba(row)[0, 1])
    return {"fraud_probability": p, "model_version": MODEL_VERSION}
# Note: the training feature order must match this row order exactly.
# For production, authenticate callers, log requests, and handle timeouts.

3. MLOps: Experiment Tracking, Versioning, Registries and CI/CD

What & Why

MLOps applies DevOps discipline to ML so that delivery is repeatable, auditable and governed. Its building blocks:

  • Experiment tracking: log parameters, metrics, data version and code version for every run so results are reproducible.
  • Model versioning and registry: a catalogue of model versions with stages/aliases (for example staging, production) and approval history.
  • CI/CD for ML: automated tests (data validation, unit tests, model-quality gates), packaging and deployment on every change; often plus continuous training when new data arrives.
  • Reproducibility: pinned dependencies, fixed random seeds, versioned data snapshots.
AnalogyLab notebooks and a controlled document system: any scientist can see exactly what was run, and only approved versions reach the factory floor.
Finance example

A model-risk committee asks "which exact model scored this customer in March, trained on which data?". With tracking and a registry the answer is one lookup instead of an investigation.

4. Production Monitoring: Data Quality, Data Drift and Concept Drift

What & Why

A deployed model decays because the world changes. Monitor three layers:

  • Operational: latency, error rate, throughput, uptime.
  • Data quality and schema: missing values, new categories, out-of-range values, changed column types.
  • Model quality: data drift (input distributions shift, e.g. average ticket size rises) and concept drift (the relationship between inputs and target changes, e.g. fraudsters adopt a new tactic). Labels often arrive late (chargebacks take weeks), so use drift in inputs and prediction scores as an early warning and track true performance when labels land.

Common drift measures: the Population Stability Index (PSI) and the Kolmogorov-Smirnov test. A widely used industry rule of thumb reads PSI < 0.1 as stable, 0.1-0.25 as moderate shift and > 0.25 as significant, but these are conventions, not statistical laws; agree thresholds with model risk.

AnalogyA car's dashboard: speed and fuel gauges (operational), a check-engine light (data quality) and a strange noise that only a mechanic recognises (concept drift): you need all three.
Finance example

After a new payment wallet launches, transaction amounts and merchant mix shift (data drift). Later, fraud rings change tactics so previously strong signals stop working (concept drift). Monitoring catches the first early and the second when chargebacks arrive.

PSI and a KS test between training and live data
import numpy as np
from scipy.stats import ks_2samp

def psi(expected, actual, bins=10, eps=1e-6):
    # Population Stability Index; bin edges come from the training ('expected') data
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, bins=edges)[0] / len(expected)
    a = np.histogram(actual, bins=edges)[0] / len(actual)
    e, a = np.clip(e, eps, None), np.clip(a, eps, None)
    return float(np.sum((a - e) * np.log(a / e)))

train_amount = X_tr["amount_aed"].to_numpy()
live_amount = train_amount * 1.3                   # simulate a shift; use real live data in production

print("PSI:", round(psi(train_amount, live_amount), 3))
stat, p = ks_2samp(train_amount, live_amount)
print("KS statistic:", round(stat, 3), " p-value:", p)

5. Retraining, Recalibration, Rollback and Securing the Pipeline

What & Why
  • Retraining: refit on fresh data on a schedule or when monitoring triggers. Re-run the full evaluation; a retrained model is a new model that needs validation and approval.
  • Recalibration: adjust predicted probabilities (for example Platt scaling or isotonic regression via CalibratedClassifierCV) when ranking is still good but the scores no longer match observed rates.
  • Rollback: keep the previous approved version deployable so a bad release can be reverted fast. Prefer staged rollouts: shadow mode, then canary traffic, then full.
  • Security: authenticate and authorise endpoint callers, encrypt data in transit and at rest, restrict who can push to the registry, scan and pin dependencies, only load trusted artefacts (pickle risk), rate-limit endpoints, and protect against attempts to probe or extract the model or craft adversarial inputs.
  • Integrity and auditability: hash artefacts, keep immutable logs of who deployed what and when, and store the inputs, outputs and model version for each decision.
AnalogyAeroplane maintenance: scheduled inspections (retraining), recalibrating instruments, a safe way back to the last certified configuration (rollback), and locked, logged access to the hangar (security).
Finance example

When drift crosses the agreed threshold, the team retrains, validates the candidate against the current champion on recent labelled data, canaries it on 5% of traffic, and rolls back automatically if the alert rate behaves abnormally.

6. Responsible AI: Fairness, Explainability and Human Oversight

What & Why
  • Fairness: models can reproduce or amplify bias in historical data. Compare outcomes (selection rate, error rates) across groups, e.g. with the demographic-parity difference or equal-opportunity (recall) gap, and investigate proxies for sensitive attributes. No single metric fits every case; the choice is a policy decision.
  • Explainability: global (which features matter overall: coefficients, permutation importance) and local (why this one decision: tools such as SHAP or LIME, which are third-party libraries). Adverse decisions on customers usually need understandable reasons.
  • Human oversight: keep a person in the loop for high-impact decisions, with the ability to review, override and contest model outputs, and clear accountability.
  • Governance: model inventory, documentation, validation, approval and periodic review. Follow your institution's policies and the guidance of your regulators; ask your compliance and model-risk teams which rules apply.
AnalogyA referee with video review: decisions are made fast, but they can be explained, challenged and overruled, and the referees are checked for consistency across teams.
Finance example

A loan-approval model is audited for approval rates across nationality groups and genders. A large gap triggers a review of features that act as proxies and, where needed, mitigation before go-live.

A simple fairness audit: selection rate per group
import pandas as pd

# `scored` has one row per application: model decision (1 = approve), true outcome and a group column
scored = pd.DataFrame({"group": g_te, "approved": (proba_te < 0.2).astype(int), "default": y_te.values})

rates = scored.groupby("group")["approved"].mean()
print(rates)
print("max gap in approval rate:", round(rates.max() - rates.min(), 3))     # demographic-parity difference

# Equal-opportunity view: among applicants who did NOT default, how often were they approved?
good = scored[scored["default"] == 0]
print(good.groupby("group")["approved"].mean())

Common Pitfalls & Anti-Patterns

⚠ Loading pickled models from untrusted places

Unpickling can run arbitrary code. Use a controlled registry, verify hashes and restrict write access.

⚠ Saving only the estimator, not the preprocessing

Serve the full Pipeline, or training and production features will silently differ (training-serving skew).

⚠ No monitoring because "accuracy was high at launch"

Models decay. Track data quality, drift, score distribution and delayed-label performance.

⚠ Retraining automatically and deploying with no validation

A bad retrain can ship bias or errors. Require quality gates and approval, and keep rollback ready.

⚠ Logging raw customer data carelessly

Logs are data too. Minimise, mask and control access to personal and financial data.

⚠ Treating fairness as one number

Different metrics can conflict. Choose and justify them with compliance and model risk.

Interactive Knowledge Check

Answer in your head (or out loud with a colleague) first, then reveal.

1. Why save the full scikit-learn Pipeline rather than just the classifier?

So preprocessing (scaling, encoding, imputation) is applied identically at inference, avoiding training-serving skew.

2. Card authorisation needs an answer in milliseconds. Batch or real-time inference?

Real-time (online) inference behind an API; batch is for scheduled scoring of many records.

3. What is the difference between data drift and concept drift?

Data drift: the input distribution changes. Concept drift: the relationship between inputs and the target changes.

4. PSI on a key feature is 0.31. What is a sensible response?

Treat it as a significant shift under the common rule of thumb: investigate the cause, check model performance (labels permitting), and consider retraining. Confirm thresholds with your model-risk policy.

5. Name two security risks specific to ML artefacts and endpoints.

Malicious pickle/serialised artefacts executing code on load; unauthenticated endpoints enabling data exfiltration, model extraction or adversarial inputs. (Also tampered models without integrity checks.)
