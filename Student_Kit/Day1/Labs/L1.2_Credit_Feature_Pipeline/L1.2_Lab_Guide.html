Credit-risk feature engineering, leakage audit and a reusable preprocessing pipeline

Engineer bank-grade credit features, prove which columns leak, split out-of-time, and ship a fitted scikit-learn pipeline that Day 3 and Day 4 reuse.

Objective & scenario alignment

Horizon Gulf Bank (HGB) is a fictional UAE retail bank with 250,000 customers. Its Board approved Project MIZAN — an AI decisioning platform covering credit, fraud, collateral valuation, cash logistics, customer retention and document automation. You are a junior ML practitioner in the MIZAN squad.

The CRO wants an honest probability-of-default (PD) model for retail lending. Your job today is the part that decides whether the model can be trusted: which columns are legitimate, which leak, which are sensitive (fairness), how the data is split in time, and a preprocessing pipeline that behaves identically in training and in production.

Progressive architecture: L3.1 (classification), L4.1 (SVR) and L4.2 (MLP) all load your feature table and pipeline.

By the end of this lab you will be able to

  • Classify every column as ID, target, post-outcome leakage, sensitive attribute or legitimate feature
  • Detect leakage quantitatively with single-feature AUC screening
  • Engineer domain features (loan-to-income, disposable income, bureau bands) in a pure, reusable function
  • Build an out-of-time train / validation / test split
  • Assemble a ColumnTransformer with imputation, log transforms, scaling, one-hot and ordinal encoding
  • Apply feature-selection fundamentals: variance, correlation and mutual information
AIP-210 exam link

AIP-210 Preparing data + Training models: feature engineering, feature selection, encoding, data leakage, train/validation/test, fit-on-train-only. Know the difference between filter (correlation, MI), wrapper (RFE) and embedded (Lasso, tree importance) selection.

1Load and assign a role to every column 10 min

Why this matters

Before engineering anything, decide what each column is. This column-role contract prevents the two most common credit-model failures: leakage and using protected attributes. Gender and nationality are kept for fairness monitoring but never used as inputs.

Your tasks

  1. Load the file with application_date parsed as a date into loans.
  2. Create lists ID_COLS, TARGET, POST_OUTCOME, SENSITIVE.
  3. Derive CANDIDATES = every other column. Print the overall default rate and the default rate by year.
Checkpoint — you should see

300,000 loans, default rate ≈ 7.5%, 2020 ≈ 12% (COVID). ~19 candidate columns.

Think like a practitioner

risk_grade was assigned by an older scorecard. Why exclude it from a challenger model? (it encodes the old model’s output — circular)

2Quantitative leakage screen 12 min

Why this matters

Opinions about leakage are not evidence. A single-feature AUC screen ranks every numeric column by how well it alone separates defaulters. Anything near 1.0 is either a miracle or a leak — and in banking it is always a leak.

Your tasks

  1. For each numeric column in CANDIDATES + POST_OUTCOME, compute roc_auc_score(y, x) on a 50k sample (fill NaN with the median; report max(auc, 1-auc)).
  2. Put results in a DataFrame sorted descending; flag suspect = auc > 0.90.
  3. Confirm that only post-outcome columns are flagged.
Checkpoint — you should see

max_days_past_due, collection_calls and loss_amount_aed top the list with AUC ≈ 0.95–1.0; the best legitimate feature (aecb_score) ≈ 0.75, then prior delinquencies ≈ 0.71.

💡 Hint

max(auc, 1-auc) makes the metric direction-free (a feature can be strongly negatively related).

Think like a practitioner

A legitimate feature scores 0.93. Is it automatically leakage? What would you investigate? (timestamp of capture, data lineage)

3Engineer credit-domain features 15 min

Why this matters

Raw columns rarely express risk the way credit officers think about it. Loan-to-income, disposable income after obligations, bureau-file status and inquiry intensity are standard underwriting concepts. Writing them as a pure function (no fitting) means it is safe to apply to any split and to production data.

Your tasks

  1. Write add_features(d) that returns a copy with: loan_to_income (= amount / annual salary), installment_to_salary, disposable_income_aed, log_salary, log_loan_amount, aecb_missing, aecb_band (Poor <580, Fair <670, Good <740, Very Good <800, Excellent), thin_file_young (age < 28 and no bureau score), employment_years, inquiries_x_dq.
  2. Apply it to loans → feat.
  3. Compare default rate by aecb_band (should be monotonic).
Checkpoint — you should see

Default rate rises steadily from Excellent (< 1%) to Poor (≈ 30%); No_File sits well above average — validating the MNAR flag from Lab 1.1.

Think like a practitioner

app_month could capture seasonality — or just noise. How will you decide whether to keep it? (validation performance, stability across years)

4Out-of-time train / validation / test split 10 min

Why this matters

A PD model is used on future applicants. Regulators and model validators expect an out-of-time (OOT) test. We train on 2019 → mid-2023, tune on the following year, and keep mid-2024 → 2025 untouched until the very end.

Your tasks

  1. Add a split column: train < 2023-07-01 ≤ valid < 2024-07-01 ≤ test.
  2. Print size and default rate per split.
  3. Explain in a markdown cell why a random split would be optimistic here.
Checkpoint — you should see

≈ 208k / 46k / 46k rows. Train default rate (≈7.9%) is higher than valid/test (≈6.7%) because it contains 2020 — real-world drift.

Think like a practitioner

The train set contains COVID-era loans with a different default regime. Keep them, drop them, or weight them? Argue both sides.

5Build the preprocessing ColumnTransformer 15 min

Why this matters

Different columns need different treatment. A ColumnTransformer bundles all of it so that fit only ever sees training rows and transform is applied identically to validation, test and production. This single object eliminates train-test contamination.

Your tasks

  1. Define NUM_LOG (money columns: log1p then scale), NUM (other numerics: median-impute + indicator, scale), CAT (one-hot, unknown-safe, rare → infrequent), ORD (employer_category, ordered), BIN (0/1 flags passthrough).
  2. Build preprocessor and fit it on the train split only.
  3. Transform the train split and print the output shape and the first 15 feature names.
Checkpoint — you should see

Roughly (207700, 46) — scaled numerics, one-hot columns and a missing-indicator for aecb_score.

💡 Hint

Use handle_unknown='infrequent_if_exist' together with min_frequency so rare emirates fold into an infrequent bucket.

Think like a practitioner

Why is aecb_score in NUM with an imputer, when we already have aecb_missing? Is the indicator now duplicated? (yes — add_indicator and aecb_missing overlap; discuss whether to remove one)

6Prove the pipeline is honest: baseline model with and without leakage 10 min

Why this matters

A feature pipeline is only finished when a model trained on it gives a credible result. We compare the honest feature set with a version that sneaks the post-outcome columns back in — the gap is the price of leakage.

Your tasks

  1. Wrap preprocessor + LogisticRegression(max_iter=2000) in a Pipeline; fit on train, report validation AUC.
  2. Repeat with max_days_past_due and collection_calls added as extra numeric inputs. Report both AUCs side by side.
Checkpoint — you should see

Honest ≈ 0.78–0.82; leaky ≈ 0.99+. Write down your honest baseline — Lab 3.1 must beat it.

Think like a practitioner

Your manager says ‘0.99 looks great, ship it’. Write the two-sentence reply.

7Feature-selection fundamentals 10 min

Why this matters

More features ≠ better model. Filter methods are fast first passes: drop near-constant columns, flag highly correlated pairs (redundant, unstable coefficients), and rank by mutual information (captures non-linear dependence).

Your tasks

  1. Using the transformed training matrix, list columns with variance < 0.01.
  2. Find feature pairs with |correlation| > 0.85.
  3. Compute mutual_info_classif on a 40k-row sample and show the top 12 features.
Checkpoint — you should see

The three ‘no bureau file’ columns (aecb_missing, aecb_band_No_File, the imputer indicator) correlate at 1.0 — the redundancy predicted in step 5. interest_rate ↔ product_Credit_Card ≈ 0.99. Bureau score, interest rate and delinquencies top the MI ranking.

Think like a practitioner

Correlated features hurt coefficient interpretation in logistic regression but rarely hurt tree ensembles. Which matters more for a regulated PD model?

  2. Save the fitted preprocessor with joblib.dump to CKPT/loan_preprocessor.joblib.

Checkpoint — you should see

Three loan_* files in checkpoints/; the reload assert passes.

Think like a practitioner

What else belongs in this contract for production? (pandas/sklearn versions, training date range, data owner, approval reference)

Stretch challenges

  1. Replace the filter step with embedded selection: fit LogisticRegression(penalty='l1', solver='saga', C=0.05) and list the features whose coefficients are exactly zero.
  2. Add target encoding for emirate with sklearn.preprocessing.TargetEncoder (internally cross-fitted). Why is naive target encoding a leakage risk?
  3. Measure Population Stability Index of debt_burden_ratio between train and test. You will formalise PSI on Day 5.

Troubleshooting

  • OneHotEncoder unexpected keyword → scikit-learn ≥ 1.2 uses sparse_output; ≥ 1.1 needed for min_frequency.
  • FunctionTransformer has no get_feature_names_out → pass feature_names_out='one-to-one'.
  • Memory error on correlation → compute it on a 50k-row sample.
