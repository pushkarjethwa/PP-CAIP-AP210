Customer master data-quality remediation

Objective & scenario alignment

Horizon Gulf Bank (HGB) is a fictional UAE retail bank with 250,000 customers. Its Board approved Project MIZAN — an AI decisioning platform covering credit, fraud, collateral valuation, cash logistics, customer retention and document automation. You are a junior ML practitioner in the MIZAN squad.

The customer master is assembled nightly from three systems (core banking, CRM, cards). Analysts complain about duplicate customers, DXB vs Dubai, salaries stored as text and impossible ages. Every MIZAN model (churn, segmentation, fraud enrichment) will read your cleaned table, so it must be correct, documented and repeatable.

Progressive architecture: your customers_clean.parquet is the input to Lab L3.2 (segmentation) and enriches later labs.

By the end of this lab you will be able to

  • Profile a large dataset programmatically and quantify data-quality issues
  • Remove PII and post-outcome (leakage) columns with a written justification
  • Standardise categoricals, parse messy numerics and mixed-format dates
  • De-duplicate at entity level, not just row level
  • Choose missing-value strategies by mechanism (MCAR / MAR / MNAR) and add missing-indicators
  • Implement a validation gate and produce a before/after DQ report
AIP-210 exam link

AIP-210 Preparing data: data-quality dimensions (completeness, validity, consistency, uniqueness), imputation strategies, handling outliers, PII. Know why MNAR missingness (e.g. no bureau file) should be flagged, not silently imputed.

1Load and profile the raw extract 10 min

Why this matters

You cannot fix what you have not measured. A reusable profile function turns ‘the data looks messy’ into numbers you can track before and after cleaning — and later in production monitoring (Day 5).

Your tasks

  1. Load customers_raw.csv into raw (keep it untouched for the final comparison).
  2. Write profile(df) returning one row per column: dtype, % missing, # unique, and 3 example values.
  3. Print the shape, the number of fully duplicated rows, and the number of duplicated customer_ids.
Checkpoint — you should see

(257500, 28), ~5,000 exact duplicates and ~7,500 duplicated IDs. account_closed_date is the most-missing column.

💡 Hint

df.isna().mean() gives the fraction missing per column. df.duplicated() returns a boolean Series.

Think like a practitioner

Why are there more duplicated IDs than duplicated rows? What does that tell you about the source systems?

2Remove PII and post-outcome (leakage) columns 10 min

Why this matters

PII (email, mobile) has no predictive legitimacy and creates privacy risk (UAE PDPL, CBUAE consumer protection). Post-outcome columns are recorded after churn happens — keeping them would leak the answer. Prove it with numbers, then drop them.

Your tasks

  1. Show the churn rate split by retention_offer_made and by whether account_closed_date is filled.
  2. Create df = copy of raw without email, mobile, account_closed_date, retention_offer_made.
  3. Record each dropped column and the reason in a dict dropped (you will export it in the report).
Checkpoint — you should see

account_closed_date filled ⇒ churn = 1.0 (perfect leak); offer made ⇒ churn ≈ 0.7 vs ≈ 0.05. Shape becomes (257500, 24).

Think like a practitioner

customer_id is also an identifier. Why do we keep it here but will never feed it to a model?

3Standardise categorical values 12 min

Why this matters

DXB, dubai and DUBAI are one emirate. If we de-duplicate before standardising, near-duplicates survive. Mapping to a controlled vocabulary and asserting the result is how production pipelines stay consistent.

Your tasks

  1. Build a function std_emirate(s) that trims, upper-cases, removes hyphens/spaces and maps codes (DXB, AUH, SHJ, AJM, RAK, FUJ, UAQ) to the 7 canonical names.
  2. Map gender variants to M/F.
  3. assert that only the 7 emirates and 2 genders remain.
Checkpoint — you should see

Exactly 7 emirates; Dubai ≈ 40%, Abu Dhabi ≈ 28%. Both asserts pass silently.

💡 Hint

Series.str.replace(r'[-\s]', '', regex=True) removes hyphens and whitespace in one call.

Think like a practitioner

A new code AAN (Al Ain) arrives next month. What does your function return, and how would the assert protect you?

4Parse messy numerics and mixed-format dates 12 min

Why this matters

Source systems disagree on formats: AED 12,500 vs 12500.0; 2019-03-04 vs 04/03/2019 vs Mar 04 2019. Parsing must be explicit (UAE dates are day-first) and every failure must be counted, never silently dropped.

Your tasks

  1. Convert monthly_salary_aed to float by stripping everything except digits and the decimal point; count values that fail to parse.
  2. Parse customer_since with pd.to_datetime(..., format='mixed', dayfirst=True); assert no new NaT values were introduced.
  3. Where tenure_months is missing, recompute it from customer_since (reference date 2025-10-31).
Checkpoint — you should see

0 salary parse failures; all dates parsed; tenure_months has no missing values.

💡 Hint

Compare the parsed dates for a row stored as 04/03/2019: with dayfirst=True you get 2019-03-04.

Think like a practitioner

Why compare against raw missing counts instead of just counting NaN after parsing?

5Validate ranges and remove entity-level duplicates 12 min

Why this matters

Validity rules encode business knowledge: customers are 18–100, balances are non-negative for this product set. Invalid ≠ delete — set to missing so the row’s other information survives. Then de-duplicate on the entity key, keeping the most complete record.

Your tasks

  1. Set age outside 18–100 to NaN; set negative avg_balance_aed to NaN. Count each.
  2. Drop exact duplicate rows.
  3. For remaining duplicated customer_ids keep the row with the fewest missing values (_n_missing helper column, sort, drop_duplicates).
  4. Assert 250,000 unique customers remain.
Checkpoint — you should see

~1,000 invalid ages, ~500 negative balances, ~5,000 exact duplicates removed, then 250,000 unique customers.

Think like a practitioner

Near-duplicates differed in digital_logins_30d by 1. Which value is true? What would you ask the source-system owner?

6Impute missing values by mechanism 14 min

Why this matters

Not all missing values are equal. aecb_score is missing mostly for new-to-country customers (MNAR) — the absence is informative, so we add a flag. Salary missingness looks random within groups (MAR) — a group median is more accurate than a global one. Final model-time imputation happens inside pipelines; here we fix what is safe and add indicators.

Your tasks

  1. Show churn rate and median tenure for rows with vs without aecb_score — is missingness random?
  2. Add aecb_missing and salary_missing 0/1 indicator columns.
  3. Impute salary with the median of its (employer_category, nationality_group) group; fall back to the global median.
  4. Fill employer_category with 'Unknown', digital_logins_30d with its median, age with the median age by employment_type.
Checkpoint — you should see

Customers without a bureau score have much shorter tenure (MNAR). Afterwards only aecb_score still has NaNs — on purpose, for the model pipeline to handle.

💡 Hint

groupby(...).transform('median') returns a Series aligned to the original rows — perfect for fillna.

Think like a practitioner

Why not fill aecb_score with 300 (the minimum)? What message would that send to a credit model?

7Type optimisation, validation gate and DQ report 10 min

Why this matters

A cleaned table is only trustworthy if a validation gate proves it. The DQ report is your audit evidence for Model Risk Management, and the parquet file (typed, compressed) is the contract with every downstream lab.

Your tasks

  1. Cast integer-like columns to integers and low-cardinality text to category; compare memory with raw.
  2. Write validate(df) with ≥ 6 rule checks returning a dict of rule → pass/fail; assert all pass.
  3. Build dq_report with before/after rows, duplicate IDs, missing %, invalid ages, distinct emirates and memory MB; save it and the parquet file to CKPT.
Checkpoint — you should see

All 8 checks True; memory falls by ≈40–45% (category dtypes, no PII strings); customers_clean.parquet written (≈10 MB).

Think like a practitioner

Turn validate() into a scheduled job: what should happen at 02:00 if seven_emirates fails? (block the load, alert the data owner, keep yesterday’s table)

Stretch challenges

  1. Package std_emirate, profile and validate into mizan_dq.py and import it — the first step towards production code.
  2. Detect statistical outliers in avg_balance_aed with the IQR rule per employer_category. Would you cap, transform or keep them?
  3. Use pandas.read_csv(..., chunksize=50_000) to compute the duplicate-ID count without loading the whole file. When would this matter?

Troubleshooting

  • ImportError: pyarrow → pip install pyarrow.
  • Assert on 250,000 fails → you de-duplicated before standardising emirate, or forgot exact duplicates.
  • Dates fail to parse → check you passed format='mixed' (pandas ≥ 2.0).
