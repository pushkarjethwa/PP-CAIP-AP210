Objective & scenario alignment

Horizon Gulf Bank (HGB) is a fictional UAE retail bank with 250,000 customers. Its Board approved Project MIZAN — an AI decisioning platform covering credit, fraud, collateral valuation, cash logistics, customer retention and document automation. You are a junior ML practitioner in the MIZAN squad.

The Head of Retention read that ‘deep learning beats everything’ and asks MIZAN to try a neural network on churn. Rather than one lucky run, you run a tuning clinic: a sequence of controlled experiments that shows the team what each hyperparameter does, ending in a fair champion vs challenger decision on the same test set as L3.4.

Progressive architecture: reuses the L3.4 split and fitted preprocessing so the comparison is exact; the decision feeds the Day 5 capstone (L5.3).

By the end of this lab you will be able to

  • Diagnose learning rates from loss curves (too small, good, divergent)
  • Relate batch size to updates per epoch, speed and noise
  • Provoke over-fitting, then cure it with dropout, L2 and early stopping
  • Compare class weights with no weights: ranking vs calibration
  • Replace one-hot encoding with embeddings using the Keras functional API
  • Make an evidence-based champion/challenger decision

1Load the champion's split and preprocessing 5 min

Why this matters

A challenger is only comparable if it sees the same rows and the same features. We reload the L3.4 split ids and reuse the champion's fitted ColumnTransformer, then convert to dense float32 arrays — the format Keras expects.

Your tasks

  1. Run the loading cell; confirm train/valid/test sizes and the champion's test PR-AUC.
  2. Write make_mlp(units, lr, dropout=0, l2=0) returning a compiled binary classifier (Adam, binary cross-entropy, AUC + PR-AUC metrics).
Checkpoint — you should see

37 input features; 150k / 50k / 50k rows; champion = logistic (test PR-AUC ≈ 0.25). The default MLP has 4,545 parameters.

2Experiment 1 — the learning rate 12 min

Why this matters

The learning rate is the single most important optimiser setting. Too small: the loss creeps down and you run out of epochs. Too large: updates overshoot and the loss bounces or explodes. The validation loss curve shows which regime you are in within a few epochs.

Your tasks

  1. For lr in 1e-5, 1e-3, 1e-2, 0.3: fit make_mlp(lr=lr) for 8 epochs, batch 512, with validation data.
  2. Plot validation loss per epoch for each lr; tabulate the best validation PR-AUC.
Checkpoint — you should see

lr 1e-5 is still far from converged after 8 epochs (PR-AUC ≈ 0.14); 1e-3 and 1e-2 converge to ≈ 0.25; 0.3 gives an erratic, higher loss curve and PR-AUC ≈ 0.19.

Think like a practitioner

Adam adapts the step per weight. Why does a far-too-large global learning rate still hurt it?

3Experiment 2 — batch size, updates and time 10 min

Why this matters

One epoch = one pass over the data; the number of updates per epoch = rows ÷ batch size. Small batches give many noisy updates (slow per epoch, good at escaping flat regions); large batches give few smooth updates (fast on hardware, may need a larger learning rate). We measure both quality and seconds.

Your tasks

  1. For batch in 32, 512, 8192 train 3 epochs with lr 1e-3; record updates/epoch, seconds and best validation PR-AUC.
  2. Repeat batch 8192 with lr 1e-2 and compare.
Checkpoint — you should see

Batch 32: 4,688 updates/epoch, ≈ 7× slower than batch 512, converged (≈ 0.25). Batch 8192 with lr 1e-3: only 19 updates/epoch — fastest but under-trained (≈ 0.20); raising lr to 1e-2 recovers most of the gap (≈ 0.24).

💡 Hint

Wall-clock numbers depend on your CPU — compare the ratios, not the absolute seconds.

4Experiment 3 — provoke over-fitting, then cure it 15 min

Why this matters

With few rows and many parameters a network memorises noise: training loss keeps falling while validation loss turns upward. The cures are the regularisers you met on Day 2 in neural form: dropout (randomly silence neurons during training), L2 weight decay, and early stopping (keep the weights from the best validation epoch).

Your tasks

  1. Take a 4,000-row training sample. Fit a wide make_mlp((256, 256)) for 60 epochs (batch 128) — plot train vs validation loss.
  2. Refit with dropout=0.4, l2=1e-3 plus EarlyStopping(patience=5, restore_best_weights=True); plot again.
  3. Report validation PR-AUC of both.
Checkpoint — you should see

Unregularised: training loss heads towards 0 while validation loss climbs after a few epochs; val PR-AUC ≈ 0.17. Regularised: the curves stay together, training stops after ≈ 25 epochs and val PR-AUC recovers to ≈ 0.23 — from only 4,000 rows.

Think like a practitioner

Early stopping uses the validation set to choose the number of epochs. Is the validation score still an unbiased estimate afterwards?

5Experiment 4 — class weights: ranking vs calibration 8 min

Why this matters

With 12% churners, class_weight={0: 1, 1: 7.3} makes each churner count as much as all non-churners together. It often changes ranking very little (PR-AUC) but pushes every probability up — the model is no longer calibrated. Retention EV maths (L3.4) needs calibrated probabilities.

Your tasks

  1. Train make_mlp() for 6 epochs with and without balanced class weights.
  2. Compare validation PR-AUC, the mean predicted probability and the actual churn rate.
Checkpoint — you should see

PR-AUC is identical (≈ 0.25), but the weighted model's mean prediction is ≈ 0.45 against an actual rate of 0.12 — badly mis-calibrated. Unweighted: 0.12, spot on.

Think like a practitioner

If you must use class weights, how could you fix calibration afterwards? (Hint: L3.1.)

6Experiment 5 — embeddings instead of one-hot 12 min

Why this matters

One-hot encoding gives every category its own independent column. An embedding layer learns a small dense vector per category, so similar categories (e.g. emirates with similar churn behaviour) end up close together — the same idea that powers word embeddings. It needs the functional API because the model has several inputs.

Your tasks

  1. Integer-encode segment, employment_type, emirate with category codes; take the scaled numeric block from the champion's preprocessing.
  2. Build a functional model: numeric input + one Embedding(n_cat, 3) per categorical → Flatten → Concatenate → Dense(64) → Dense(32) → sigmoid.
  3. Train 8 epochs; compare validation PR-AUC with the one-hot MLP; print the learned emirate vectors.
Checkpoint — you should see

Embeddings match the one-hot MLP (within ≈ 0.005 PR-AUC) — with only 7 emirates there is little to gain; embeddings shine with hundreds of categories (merchants, branches, products). The 7 learned emirate vectors are printed.

💡 Hint

Each categorical needs its own Input with dtype='int32'; pass a dict whose keys match the input names.

7Final challenger vs champion on the test set 10 min

Why this matters

Now combine what worked — lr 1e-3, batch 512, moderate dropout, early stopping on validation — train on the full training set and score the test set once, exactly as the champion was. A challenger replaces the champion only if it is materially better (here: ≥ 0.01 PR-AUC), because a neural network costs more to run, explain and govern.

Your tasks

  1. Train make_mlp((128, 64), lr=1e-3, dropout=0.2) up to 40 epochs with early stopping (patience 4).
  2. Compute test ROC-AUC, PR-AUC and capture@10% next to the champion's; decide KEEP or REPLACE.
  3. Save the MLP and nn_tuning_results.json (all experiments + the decision).
Checkpoint — you should see

The MLP lands slightly below the logistic champion (PR-AUC ≈ 0.247 vs 0.251) → KEEP champion. Deep learning does not win on small, tabular, mostly-linear problems; it wins on images (L4.2's CNN: 97% vs 69%) and sequences.

Think like a practitioner

Write the one-paragraph note to the Head of Retention explaining why the neural network was not deployed.

Stretch challenges

  1. Use keras_tuner (pip install keras-tuner) to run a Bayesian search over units, dropout and learning rate. Does it beat your hand-tuned model?
  2. Add a learning-rate schedule (keras.optimizers.schedules.ExponentialDecay). Does it allow a larger starting lr?
  3. Ensemble: average the MLP's and the logistic champion's probabilities. Does the blend beat both on validation?

Troubleshooting

  • Training slow → reduce epochs, or use batch 1024 with lr 2e-3.
  • val_pr_auc key error → the metric name must be exactly pr_auc in make_mlp.
  • Embedding index error → an unseen category got code −1; use the training categories list (codes) for every split.
